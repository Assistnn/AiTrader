# 16. 実行エンジンとUI接続 設計書

## 1. 概要

本設計書は、Phase 1-4で実装済みの全コンポーネント（決定パイプライン、セーフガード、AI統合、取引所抽象化、フロントエンド）を「実際に動く自動取引システム」として統合するための設計を定義する。

### 1-1. スコープ

- 取引所API実通信（GMO Coin FX / bitbank Crypto）
- 自動実行エンジン（TradeExecutionEngine）
- リアルタイムデータフィード（WebSocket + REST API）
- UI操作 → エンジン制御の接続
- 設定変更のランタイム反映（ホットリロード）
- WebSocketイベント統合（サービス層 → フロントエンド）
- ポジション管理と退出管理
- 経済指標カレンダー外部API連携
- エラーハンドリングとリカバリ

### 1-2. 非スコープ

- 新規画面追加（フロントエンドは Phase 3-4 で完成済み）
- パイプラインロジックの変更（M1-M4, MX は変更なし）
- メール送信（SMTP統合は別途）

### 1-3. 設計思想

既存設計書の設計思想を継承する:

1. **生存性最優先**: エンジン異常時は全ポジション強制決済 → 停止
2. **透明性**: 全判定・全注文をログ記録
3. **デバッグ容易性**: `_debug` フィールドで中間計算値を保存
4. **安全側に倒す**: 不明・異常時は NO_TRADE（何もしない）

## 2. TradeExecutionEngine アーキテクチャ

### 2-1. 全体構成

```
FastAPI Application
  └── lifespan (startup/shutdown)
        └── EngineManager (singleton)
              ├── TradeExecutionEngine[trader_1] (asyncio.Task)
              │     ├── MarketDataFeed → BarBuilder → IndicatorEngine → StateBuilder
              │     ├── GuardEngine
              │     ├── DecisionOrchestrator (M1→M2→MX→M3→M4)
              │     ├── ExecutionEngine (注文発行/決済)
              │     └── ConfigEventBus (設定変更受信)
              ├── TradeExecutionEngine[trader_2]
              └── ...
```

### 2-2. EngineManager

全トレーダーのエンジンを一元管理するシングルトン。

**デプロイ制約:** EngineManagerはプロセス内シングルトンのため、uvicorn のworker数は必ず **1** とすること。workers>1の場合、各workerプロセスが独立したEngineManagerインスタンスを持ち、同一トレーダーのエンジンが重複起動する。

```python
class EngineManager:
    """全トレーダーのエンジンライフサイクルを管理する。"""

    _engines: dict[int, TradeExecutionEngine]  # trader_id → engine
    _tasks: dict[int, asyncio.Task]            # trader_id → asyncio task
    _config_bus: ConfigEventBus

    async def start_trader(self, trader_id: int, db: AsyncSession) -> None
    async def stop_trader(self, trader_id: int, force_close: bool = False) -> None
    async def stop_all(self) -> None
    async def reload_config(self, trader_id: int, config_type: str, new_config: dict) -> None
    def get_engine_status(self, trader_id: int) -> EngineStatus | None
    async def startup(self, db: AsyncSession) -> None   # lifespan startup
    async def shutdown(self) -> None                      # lifespan shutdown
```

**ライフサイクル:**

1. `startup()`: DB から `status="running"` の全トレーダーを検索し、各エンジンを起動
2. `start_trader()`: エンジンインスタンス生成 → ウォームアップ → asyncio.Task として起動
3. `stop_trader()`: asyncio.Task をキャンセル → リソース解放
4. `shutdown()`: 全エンジンを順次停止

### 2-3. TradeExecutionEngine

トレーダー1つに対応するメインループ。

```python
class TradeExecutionEngine:
    """1トレーダーのイベント駆動取引エンジン。"""

    trader_id: int
    exchange: BaseExchange
    data_provider: BaseDataProvider
    orchestrator: DecisionOrchestrator
    guard_engine: GuardEngine
    execution_engine: ExecutionEngine
    indicator_engine: IndicatorEngine
    state_builder: StateBuilder
    bar_scheduler: BarConfirmationScheduler
    config_bus: ConfigEventBus
    _lock: asyncio.Lock  # 同一トレーダーの並行実行防止

    async def run(self) -> None           # メインループ
    async def warmup(self) -> None        # ウォームアップ（初期データ取得）
    async def cleanup(self) -> None       # リソース解放
```

**メインループ (`run()`) の処理フロー:**

```
while running:
    1. ConfigEventBus から設定変更イベントを消費（非ブロッキング）
    2. BarConfirmationScheduler から足確定イベントを取得（タイムアウト付き待機）
    3. 足確定イベントに応じて:
       - H1確定 → M1パイプライン実行
       - M15確定 & M1=PASS → M2パイプライン実行
       - M5確定 & M1+M2=PASS → M3パイプライン実行（エントリー判定）
       - M1確定 & ポジション保有中 → M4退出管理
    4. パイプライン結果に応じて:
       - action=ENTRY → ExecutionEngine.execute_entry()
       - M4.action=EXIT → ExecutionEngine.execute_exit()
    5. ポジション同期（30秒毎）
    6. ログDB永続化
    7. WebSocket通知
```

### 2-4. ウォームアップ

エンジン起動時に、IndicatorEngine のウォームアップ期間分のデータを事前取得する。

```
必要データ:
  - D1足: 200本（EMA200のウォームアップ）
  - H4足: 200本
  - H1足: 200本
  - M30足: 50本
  - M15足: 50本
  - M5足: 50本
  - M1足: 50本

取得方法: data_provider.get_historical_ohlcv() → BarBuilder → IndicatorEngine.update()
```

## 3. 取引所API実装仕様

### 3-1. GMO Coin FX

**ベースURL:**
- Public: `https://forex-api.coin.z.com/public`
- Private: `https://forex-api.coin.z.com/private`

**認証:** 既存の `_sign()` / `_headers()` メソッドを活用（HMAC-SHA256、実装済み）

**メソッドマッピング:**

| BaseExchange メソッド | GMO Coin API | HTTP Method | Path |
|---|---|---|---|
| `get_ticker(pair)` | Ticker | GET | `/v1/ticker?symbol={pair}` |
| `get_ohlcv(pair, tf, limit)` | KLines | GET | `/v1/klines?symbol={pair}&interval={tf}&date={date}` |
| `place_order(...)` | New Order | POST | `/v1/order` |
| `cancel_order(id)` | Cancel Orders | POST | `/v1/cancelOrders` |
| `get_order_status(id)` | Order Info | GET | `/v1/orders?orderId={id}` |
| `get_positions()` | Open Positions | GET | `/v1/openPositions` |
| `close_position(id, amount)` | Close Order | POST | `/v1/closeOrder` |
| `get_balance()` | Account Assets | GET | `/v1/account/assets` |
| `modify_order(id, price)` | Change Order | POST | `/v1/changeOrder` |

**TP/SL 実装方式:**

`BaseExchange.place_order()` のシグネチャ（06書§2定義）に含まれる `tp_price` / `sl_price` パラメータは、取引所によって扱いが異なる。TP/SL の実際の注文発行は `ExecutionEngine` 層が責任を持つ:

- GMO Coin FX: `place_order()` では `tp_price`/`sl_price` を無視し MARKET 注文のみ発行
- 約定確認後、`ExecutionEngine` が OCO 注文（利確: LIMIT + 損切: STOP）を別途 `place_order()` で発行
- OCO の紐付けは `clientOrderId` のプレフィックスで管理（例: `entry-{uuid}`, `tp-{uuid}`, `sl-{uuid}`）

**レートリミット:**
- Private API: 1秒あたり1リクエスト（GMO Coin 公式制限）
- 既存の `OrderRateLimiter` を使用

**HTTPクライアント:**
- `httpx.AsyncClient` を使用（既存AIプロバイダーと統一）
- コネクションプール: `limits=httpx.Limits(max_connections=10, max_keepalive_connections=5)`
- タイムアウト: `httpx.Timeout(10.0, connect=5.0)`

### 3-2. bitbank

**ベースURL:**
- Public: `https://public.bitbank.cc`
- Private: `https://api.bitbank.cc`

**認証:** 既存の `_sign_get()` / `_sign_post()` / `_headers()` メソッドを活用（HMAC-SHA256、実装済み）

**メソッドマッピング:**

| BaseExchange メソッド | bitbank API | HTTP Method | Path |
|---|---|---|---|
| `get_ticker(pair)` | Ticker | GET | `/{pair}/ticker` |
| `get_ohlcv(pair, tf, limit)` | Candlestick | GET | `/{pair}/candlestick/{type}/{date}` |
| `place_order(...)` | Create Order | POST | `/v1/user/spot/order` |
| `cancel_order(id)` | Cancel Order | POST | `/v1/user/spot/cancel_order` |
| `get_order_status(id)` | Order Info | GET | `/v1/user/spot/order?pair={pair}&order_id={id}` |
| `get_positions()` | Assets | GET | `/v1/user/assets` |
| `close_position(id, amount)` | 売り注文で決済 | POST | `/v1/user/spot/order` |
| `get_balance()` | Assets | GET | `/v1/user/assets` |
| `modify_order(id, price)` | キャンセル + 再注文 | - | cancel_order → place_order |

**Spot 取引固有の制約:**
- ポジション概念なし → 残高ベースの仮想ポジション管理
- `get_positions()`: DB上のPosition レコードから仮想ポジション一覧を返却
- `close_position()`: 保有通貨の売却注文（SELL MARKET）を発行
- TP/SL: API非対応のため、`place_order()` の `tp_price`/`sl_price` は無視。`ExecutionEngine` がシステム側で M1足毎に価格監視し、条件到達時に成行決済（§9-4参照）

**レートリミット:**
- 既存の `OrderRateLimiter(max_per_second=6)` を使用（bitbank 固有制限）

## 4. リアルタイムデータフィード

### 4-1. ハイブリッド方式

データ取得は2つの方式を併用し、信頼性を確保する:

**方式A（主）: KLine API ポーリング**
- 各時間足の確定タイミングで REST API を呼び出し、確定足を取得
- 確実性が高く、WebSocket 切断の影響を受けない

**方式B（補）: WebSocket ティック**
- GMO Coin: `wss://forex-api.coin.z.com/ws/public/v1`
- bitbank: `wss://stream.bitbank.cc/socket.io/` （Socket.IO プロトコル）
- ティックデータを `BarBuilder.on_tick()` に供給
- WebSocket 切断時は方式A にフォールバック

### 4-2. BarConfirmationScheduler

足確定タイミングを管理し、`BarClosedEvent` を発行する。

```python
@dataclass
class BarClosedEvent:
    pair: str
    timeframe: str          # "M1" | "M5" | "M15" | "M30" | "H1" | "H4" | "D1"
    timestamp: datetime     # 足の開始時刻（UTC）
    ohlcv: OHLCV

class BarConfirmationScheduler:
    """足確定タイミングを管理する。"""

    async def wait_for_next_event(self, timeout: float = 60.0) -> BarClosedEvent | None
    async def start(self, pairs: list[str], data_provider: BaseDataProvider) -> None
    async def stop(self) -> None
```

**足確定タイミング（UTC基準）:**

| 時間足 | 確定タイミング | ポーリング間隔 |
|---|---|---|
| M1 | 毎分 00秒 | 5秒（確定直後に取得） |
| M5 | 5分毎 00秒 | 5秒 |
| M15 | 15分毎 00秒 | 5秒 |
| M30 | 30分毎 00秒 | 5秒 |
| H1 | 毎時 00分 | 10秒 |
| H4 | 0/4/8/12/16/20時 00分 | 10秒 |
| D1 | UTC 00:00（GMO） / 15:00（bitbank） | 30秒 |

### 4-3. MarketDataFeed

取引所 WebSocket への接続を管理し、ティックデータを配信する。

```python
class MarketDataFeed:
    """取引所WebSocket接続の管理。"""

    async def connect(self, pairs: list[str]) -> None
    async def disconnect(self) -> None
    async def on_tick(self, pair: str, ticker: Ticker) -> None  # BarBuilder呼出
    def is_connected(self) -> bool
```

**再接続ロジック:**
- 切断検知 → 指数バックオフ: 1s → 2s → 4s → 8s → 16s → 32s → max 60s
- 5分以上の連続切断 → `alerts` チャネルで通知
- 再接続成功後、直近の確定足を REST API で補完

## 5. イベント駆動パイプライン実行

### 5-1. 実行タイミング（設計書02/04準拠）

| パイプライン | トリガー | 実行条件 | 最大頻度 |
|---|---|---|---|
| M1（方向判定） | H1足確定 | なし | 1回/時間 |
| M2（セットアップ） | M15足確定 | M1結果=PASS | 4回/時間 |
| M3（エントリー） | M5足確定 | M1+M2結果=PASS | 12回/時間 |
| M4（退出管理） | M1足確定 | ポジション保有中 | 60回/時間 |

**PASS判定基準の定義（04_判断パイプライン JudgeOutput との対応）:**

各ステージの `JudgeOutput` は `result: dict[str, Any]` を返すが、後続ステージへの実行条件判定には以下の基準を使用する:

| ステージ | PASS条件 | 根拠 |
|---|---|---|
| M1（方向判定） | `M1Output.trade_allowed == true` | 04書§3-1: trade_allowed はトレンド・レジーム・ボラティリティの総合判定結果 |
| M2（セットアップ） | `M2Output.setup_valid == true` | 04書§4-3: セットアップ成立の場合にtrue |

M1/M2 いずれかが PASS でない場合、後続ステージはスキップされ `pipeline_logs` にスキップ理由が記録される。

### 5-2. M1/M2結果キャッシュ

```python
@dataclass
class PipelineCacheEntry:
    output: JudgeOutput
    timestamp: datetime          # 判定時刻
    valid_until: datetime        # 次回足確定まで有効
    bar_timestamp: datetime      # 判定に使用した足の時刻

class PipelineCache:
    """M1/M2の判定結果をキャッシュする。"""

    m1_cache: dict[str, PipelineCacheEntry]  # pair → cache
    m2_cache: dict[str, PipelineCacheEntry]

    def get_m1(self, pair: str) -> JudgeOutput | None
    def get_m2(self, pair: str) -> JudgeOutput | None
    def set_m1(self, pair: str, output: JudgeOutput, bar_ts: datetime) -> None
    def set_m2(self, pair: str, output: JudgeOutput, bar_ts: datetime) -> None
    def invalidate(self, pair: str) -> None
```

### 5-3. パイプライン実行フロー

```
足確定イベント受信
  │
  ├── H1確定
  │     └── M1実行 → キャッシュ更新
  │
  ├── M15確定
  │     ├── M1キャッシュ確認 → PASS でなければスキップ
  │     └── M2実行 → キャッシュ更新
  │
  ├── M5確定
  │     ├── M1+M2キャッシュ確認 → 両方PASS でなければスキップ
  │     └── M3実行（Orchestrator.execute_pipeline()）
  │           ├── action=ENTRY → ExecutionEngine.execute_entry()
  │           └── action=NO_TRADE → ログ記録のみ
  │
  └── M1確定 & ポジション保有中
        └── M4実行
              ├── action=EXIT → ExecutionEngine.execute_exit()
              ├── action=ADJUST_SL → ExecutionEngine.adjust_stop_loss()
              └── action=HOLD → 何もしない
```

### 5-4. 並行実行制御

- 同一トレーダーのパイプライン実行は `asyncio.Lock` で排他制御
- M3実行中に次のM1足確定が来た場合、M3完了後にM1を実行
- M4（退出管理）は別ロックで独立実行可能

## 6. UI操作 → エンジン制御の接続仕様

### 6-1. トレーダー開始

```
POST /traders/{id}/start
  │
  ├── 1. 所有権検証（@verify_ownership）
  ├── 2. DB更新: trader.status = "running"
  ├── 3. EngineManager.start_trader(trader_id, db)
  │     ├── ExchangeFactory.create_exchange(mode="live", ...)
  │     ├── ExchangeFactory.create_data_provider(trade_type)
  │     ├── TradeExecutionEngine 生成
  │     ├── engine.warmup()  # ヒストリカルデータ取得
  │     └── asyncio.create_task(engine.run())
  ├── 4. WebSocket通知: trader_updates {status: "running"}
  └── 5. レスポンス: {status: "ok", data: {traderId, status: "running"}}
```

**前提条件チェック（start時）:**
- 取引所APIキーが設定済みか
- APIキーの認証テスト（`exchange.get_balance()` で疎通確認）
- 前提条件を満たさない場合は 400 Bad Request

### 6-2. トレーダー停止

```
POST /traders/{id}/stop
  │
  ├── 1. 所有権検証
  ├── 2. EngineManager.stop_trader(trader_id, force_close=false)
  │     ├── asyncio.Task キャンセル
  │     ├── engine.cleanup()
  │     └── (force_close=true の場合) 全ポジション決済
  ├── 3. DB更新: trader.status = "stopped"
  ├── 4. WebSocket通知: trader_updates {status: "stopped"}
  └── 5. レスポンス: {status: "ok"}
```

### 6-3. 全ポジション決済

```
POST /traders/{id}/close-all
  │
  ├── 1. 所有権検証
  ├── 2. engine = EngineManager.get_engine(trader_id)
  ├── 3. positions = await exchange.get_positions()
  ├── 4. for pos in positions:
  │     └── await exchange.close_position(pos.position_id)
  ├── 5. DB の Position レコード更新（status="closed"）
  ├── 6. TradeHistory レコード作成（実損益記録）
  ├── 7. WebSocket通知: trader_updates {positions: []}
  └── 8. レスポンス: {status: "ok", data: {closedCount}}
```

### 6-4. トレーダー設定変更時のエンジン再起動

```
PUT /traders/{id}
  │
  ├── 1. 所有権検証
  ├── 2. DB更新: trader の各フィールドを更新
  ├── 3. エンジンが running の場合:
  │     ├── EngineManager.stop_trader(trader_id, force_close=false)
  │     ├── 新しい設定で ExchangeConfig 取得（APIキー復号）
  │     └── EngineManager.start_trader(trader_id, ...) ← 新設定で再起動
  └── 4. レスポンス: {status: "ok", data: {trader}}
```

**再起動の理由:**
- trade_type 変更（FX↔Crypto）: Exchange/DataProvider の入替が必要
- symbols 変更: MarketDataFeed/BarScheduler の再接続・warmup が必要
- その他のフィールド変更: ConfigEventBus のホットリロード（§7）では対応できない構造的変更に対して、stop→start が最も安全

**注意:** force_close=false のため、オープンポジションは保持される。

### 6-5. ダッシュボード一括操作

| エンドポイント | 処理 |
|---|---|
| `POST /dashboard/start-all` | 全トレーダーに対して `EngineManager.start_trader()` |
| `POST /dashboard/stop-all` | `EngineManager.stop_all()` |
| `POST /dashboard/close-all` | 全トレーダーの全ポジション決済後、停止 |

## 7. 設定変更のランタイム反映（ホットリロード）

### 7-1. ConfigEventBus

```python
@dataclass
class ConfigChangeEvent:
    trader_id: int
    config_type: str    # "model_stage" | "safeguard" | "trader"
    stage: str | None   # "M1" | "M2" | "M3" | "M4" | None
    new_config: dict
    timestamp: datetime

class ConfigEventBus:
    """asyncio.Queue ベースの軽量イベントバス。"""

    _queues: dict[int, asyncio.Queue[ConfigChangeEvent]]

    def subscribe(self, trader_id: int) -> asyncio.Queue[ConfigChangeEvent]
    def unsubscribe(self, trader_id: int) -> None
    async def publish(self, event: ConfigChangeEvent) -> None
```

### 7-2. API → ConfigEventBus → エンジン

```
PUT /traders/{id}/model-stages/{stage}
  │
  ├── 1. DB更新（既存処理）
  ├── 2. ConfigChange レコード作成（既存処理）
  └── 3. ConfigEventBus.publish(ConfigChangeEvent(...))
        └── エンジンのメインループで消費
              └── Judge の config を差し替え（次のパイプライン実行から反映）

PUT /traders/{id}/safeguards
  │
  ├── 1. DB更新（既存処理）
  ├── 2. ConfigChange レコード作成（既存処理）
  └── 3. ConfigEventBus.publish(ConfigChangeEvent(...))
        └── エンジンの GuardEngine.reload_config(new_config)
```

### 7-3. エンジン側の設定消費

```
TradeExecutionEngine._process_config_events():
  1. ConfigEventBus キューから非ブロッキングで取得
  2. config_type == "model_stage" の場合:
     - DB model_stage_configs から該当ステージの config_json を再ロード
     - self._judge_configs[stage] を更新
     - 次回パイプライン実行から新設定を使用
  3. config_type == "safeguard" の場合:
     - GuardEngine.reload_config(new_config) を呼出
```

### 7-4. エンジン起動時の設定ロード

```
EngineManager.start_trader():
  1. DB model_stage_configs を trader_id で一括取得
  2. 各ステージ(m1-m4)の config_json → JudgeConfig に変換
  3. TradeExecutionEngine に judge_configs dict として渡す
  4. AI APIキーが環境変数に設定されている場合:
     - create_provider() で BaseAIProvider を生成
     - AIJudgeHelper を構築し、各 Judge に渡す
  5. AI APIキーが未設定の場合:
     - ai_helper=None（ルールモードにフォールバック）
     - WARNING ログ出力
```

### 7-5. 安全対策

- パイプライン実行中（`_lock` 取得中）の設定変更は、実行完了後に適用
- 設定変更適用時に `pipeline_logs` に変更適用ログを記録

### 9-2. 注文実行フロー（execute_entry）

```
1. PositionSizer による最終ロットサイズ確認
2. clientOrderId 生成（UUID、二重発注防止）
3. OrderRateLimiter.wait()
4. exchange.place_order(MARKET, ...)
5. 約定確認（get_order_status でポーリング、最大10秒）
6. 約定後:
   - GMO FX: TP/SL として OCO 注文発行
   - bitbank: SL/TP 監視リストに追加（システム側監視）
7. DB: Position レコード作成
8. DB: PipelineLog に execution_result を追記
9. WebSocket: trader_updates で通知
```

### 9-3. ポジション同期

取引所の実ポジションと DB の整合性を定期的に確認する。

```
30秒毎:
  1. exchange.get_positions() / exchange.get_balance()
  2. DB上のPositionレコードと比較
  3. 乖離検知時:
     - DB側にない実ポジション → DB にレコード追加 + アラート
     - 取引所側にないDBレコード → DB レコードを closed に更新
     - 数量差異 → ログ記録 + アラート
```

```
M1足確定毎（毎分）:

     - SL到達 → exchange.close_position() で成行売却
```

### 10-1. データソース

外部 API から経済指標イベントを取得し、セーフガード SG-027〜SG-031 で利用する。

**候補データソース（優先順）:**

| データソース | 形式 | 認証 | 更新頻度 | 備考 |
|---|---|---|---|---|
| FXStreet Economic Calendar API | JSON | 不要（公開） | リアルタイム | 構造化データ、重要度付き |
| Forex Factory RSS/Scraping | XML/HTML | 不要 | 数時間毎 | 最も普及、ただしスクレイピング |
| Investing.com Calendar | JSON | 不要 | リアルタイム | API制限厳しい |

**選定基準:** 無料 + 構造化データ + 重要度(impact)情報を含むこと

### 10-2. EconomicCalendarFetcher

```python
@dataclass
class EconomicEvent:
    event_id: str
    title: str
    country: str            # "US" | "JP" | "EU" | "GB" | "AU" | ...
    importance: int          # 1(低) | 2(中) | 3(高)
    event_datetime: datetime # UTC
    currency: str            # "USD" | "JPY" | ...
    actual: str | None
    forecast: str | None
    previous: str | None

class EconomicCalendarFetcher:
    """経済指標データを外部APIから定期取得しキャッシュする。"""

    async def fetch_events(self, start: datetime, end: datetime) -> list[EconomicEvent]
    async def get_upcoming_events(self, hours_ahead: int = 24) -> list[EconomicEvent]
    def get_cached_events(self) -> list[EconomicEvent]
```

### 10-3. GuardEngine 連携

```
TradeExecutionEngine メインループ:
  - 起動時: fetch_events() で当日+翌日のイベントを取得
  - 6時間毎: fetch_events() でキャッシュ更新
  - 取得失敗時: 安全側に倒す（全イベント発表中と見なし、取引停止）

GuardEngine.evaluate_all() への注入:
  - SG-027: upcoming_events リストを GuardEngine に渡す
  - SG-028: importance >= config.min_importance でフィルタ
  - SG-029: event_datetime - config.pre_stop_minutes 以内なら BLOCK
  - SG-030: event_datetime + config.post_stop_minutes 以内なら BLOCK
  - SG-031: config.scope == "tradedOnly" の場合、取引通貨のみフィルタ
```

### 10-4. フォールバック

- API通信失敗 → キャッシュが有効なら使用
- キャッシュも期限切れ → **安全側: 全指標発表中と見なして新規エントリー停止**
- ログに警告記録、`alerts` チャネルで通知

## 11. エラーハンドリングとリカバリ

### 11-1. リトライ戦略

```python
class RetryWithBackoff:
    """指数バックオフリトライデコレータ。"""

    max_retries: int = 3
    base_delay: float = 1.0    # 秒
    max_delay: float = 60.0    # 秒
    backoff_factor: float = 2.0
    retryable_exceptions: tuple = (httpx.TimeoutException, httpx.NetworkError)
```

**リトライ対象と非対象:**

| エラー種別 | リトライ | 対応 |
|---|---|---|
| ネットワークタイムアウト | する（最大3回） | 指数バックオフ |
| HTTP 429 (Rate Limit) | する（Retry-After ヘッダー準拠） | 待機後リトライ |
| HTTP 500/502/503 | する（最大3回） | 指数バックオフ |
| HTTP 401/403 (認証) | しない | 即座にエンジン停止 |
| 注文拒否 (400) | しない | ログ記録、NO_TRADE |

### 11-2. サーキットブレーカー

```python
class CircuitBreaker:
    """連続失敗時にリクエストを一時停止する。"""

    failure_threshold: int = 5      # 連続失敗回数
    recovery_timeout: float = 300.0 # 5分後にハーフオープン
    state: str  # "closed" | "open" | "half_open"
```

### 11-3. エンジン自動再起動

```
エンジン内で未処理例外発生
  │
  ├── restart_count < 3
  │     ├── ログ記録: "Engine restarting (attempt {n})"
  │     ├── 30秒待機
  │     └── engine.warmup() → engine.run() 再開
  │
  └── restart_count >= 3
        ├── ログ記録: "Engine HALTED after 3 failures"
        ├── DB更新: trader.status = "halted"
        ├── 全ポジション強制決済を試行
        └── WebSocket通知: alerts {type: "engine_halted"}
```

### 11-4. 取引所メンテナンス対応

| 検知方法 | 対応 |
|---|---|
| HTTP 503 応答 | CircuitBreaker で一時停止 → 5分後に再試行 |
| 定期メンテナンス時間帯 | 設定で管理（例: 日本時間 6:00-6:15）、スキップ |
| WebSocket 切断 + REST 失敗 | 全断と判断 → エンジン一時停止、アラート通知 |

## 12. 監査対応

### 12-1. 既存監査項目の継承

| 監査項目 | 実行エンジンでの対応 |
|---|---|
| 【監査1】テナント隔離 | EngineManager が trader.user_id を検証。エンジンは自トレーダーのデータのみアクセス |
| 【監査2】タイムトラベル防止 | BarConfirmationScheduler は確定足のみ使用。不完全足は StateBuilder に渡さない |
| 【監査3】プロンプトインジェクション | AI呼出パスは既存の PromptAssembler/ResponseParser を経由（変更なし） |
| 【監査4】AI フェイルセーフ | AI異常時の HOLD フォールバックは既存（変更なし） |

### 12-2. 新規監査項目

**【監査5】注文発行→約定確認の整合性検証**
- `place_order()` 後に `get_order_status()` で約定を確認
- 10秒以内に FILLED にならない場合 → `cancel_order()` で取消
- 部分約定の検知と処理（残量のキャンセル or 追加注文）
- `clientOrderId` による二重発注防止

**【監査6】ポジション同期の乖離検知**
- 30秒毎のポジション同期で乖離を検知
- 乖離検知時は `alerts` チャネルで通知 + ログ記録
- 致命的乖離（DB にないポジションが取引所に存在）は手動対応を要求

**【監査7】強制停止時の全決済完了確認**
- HALT 時の強制決済は `close_all_positions()` で一括実行
- 決済失敗（取引所エラー）の場合は 30秒後にリトライ（最大3回）
- 全決済完了を確認できるまでエンジンは shutdown しない
- 決済完了できない場合は CRITICAL ログ + アラート通知（手動介入要求）
